Summary

The capture records one authorized recon run against 192.168.50.0/24. The actual attack signature is a minority of the traffic — the bulk is the operator's own SSH session plus ambient network noise. Breaking it into four buckets (signal / leak / operator / noise) is what makes the real recon legible, and it surfaced two items worth acting on.

Recon signal — ARP sweep + SYN + Modbus (~1,180 fr) DNS leak to 8.8.8.8 (134 fr) Operator SSH (515 fr) Ambient noise — mDNS/IGMP/broadcast/other ARP

Shares are of total frames; ARP (1,177 fr) spans both the scan sweep and background resolution.

B Scan side-effect leaking externally

nmap was not run with -n, so it did reverse-DNS on its targets. Those PTR queries went to an external resolver:

QuerySent toMeaning
23.50.168.192.in-addr.arpa8.8.8.8Reverse lookup of lab host .23

134 DNS frames total — internal target IPs leaked to Google DNS in cleartext.
Fix / stealth: add -n to the nmap steps so the scan resolves nothing. This keeps your target list off an external resolver and removes an easy detection/forensic breadcrumb — directly relevant to running recon quietly.

Display filters to isolate the attack

To replay just the recon for the report, drop the operator and noise:

  • Host sweep: arp.opcode==1 && ip.src==192.168.50.40 (the .40 ARP, not background)
  • Port scan: tcp.flags.syn==1 && tcp.flags.ack==0
  • Modbus probe: mbtcp
  • Exclude your own traffic/noise: !(ssh || mdns || ip.dst==255.255.255.255)
