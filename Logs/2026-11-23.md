### S9 — root cause found and fixed (not yet re-run)
- **Symptom:** Luis reported no visible effect — no heartbeat freeze, SCADA unaffected.
- **Investigation:** rather than blindly raise N again, read the actual `emelianov/modbus-esp8266`
  library source on GitHub (`src/ModbusSettings.h`, `src/ModbusTCPTemplate.h`) via a web-fetch
  subagent. **Verified facts:** `MODBUSIP_MAX_CLIENTS` = 8 on ESP32 (4 on other platforms);
  `MODBUSIP_UNIQUE_CLIENTS` is also enabled, and its documented behavior is "a new connection
  from an IP that already has a slot replaces the old one before the free-slot search."
- **Root cause:** every held connection in `s09_dos.py`/`s15_multitarget_dos.py` came from Kali's
  *one* source IP, so each new connection evicted the attacker's own previous one — never
  occupying more than **1 of 8 slots**, no matter how large N was. Raising N could never have
  worked; this was a technique-design flaw, not a tuning problem.
- **Fix:** rewrote both scripts to accept a `SOURCE_IPS` argument — one held connection per
  listed local IP, each bound explicitly (`socket.bind((ip, 0))`), so the ESP32 sees genuinely
  distinct clients. Needs secondary IPs added to Kali's `eth0` first (`sudo ip addr add
  192.168.50.23{1..8}/24 dev eth0`, picked outside any live-seen range). The slot limit is
  per-target, so the same IP pool works against both S15 targets at once. **Not yet re-run with
  the fix** — next session.
- Old single-IP behavior kept in both scripts (no `SOURCE_IPS` given) for side-by-side contrast,
  with an explicit warning printed that it will not actually isolate the node.

## S9 conclusion — connection-exhaustion vector ruled out; SYN flood works but exceeds scope

- **Connection-slot exhaustion (the `SOURCE_IPS` fix) empirically ruled out.** Retried with 10
  distinct local source IPs held against `.14` for 45s; **packet capture proves all 10 completed
  their handshake and stayed open the entire window with zero rejections** (no RST/FIN until the
  script's own deliberate close at the end) — `S09_dos_v2.pcap`, 76 relevant packets, 11 distinct
  connections, hash `29d6667babcfb14943ab76199161cdab09fb40e8a8c41e221fbe95b3c4288154`. This
  **contradicts the generic `MODBUSIP_MAX_CLIENTS=8` read from GitHub `master`** on Nov 23 earlier
  today — the real installed firmware's effective limit is higher than 10, or (more likely) the
  OpenPLC master doesn't hold one persistent slot the way we assumed, so there was nothing to
  starve it out of. **This bench result overrides the generic library-source reading** per the
  verified/reported/assumed rule. SCADA: heartbeat did not freeze during this run (Luis-confirmed).
- **Tried the alternative vector already listed in `Scenarios.md` #9(b): a raw SYN flood**
  (`sudo hping3 -S -p 502 --flood 192.168.50.14`), run for **131 seconds** (longer than the ~15–20s
  suggested) at **~94,000 packets/sec** — **12,320,242 SYN packets sent, only 144 SYN-ACK replies
  received (~0.001% response rate)**. Captured in `S09_hping.pcap` — **862 MB, ~12.3M packets**;
  too large to keep as report evidence as-is, flagged to redo at 2–3 seconds for a right-sized
  sample (the mechanism is already proven; no need for the full 131s capture).
- **Result exceeded Scenario 9's intended scope — this is the real finding.** Luis observed **all
  eight Campus_Map dots go red**, not just `.14`'s, and the **Ignition Gateway web UI itself became
  unreachable** during the flood. At ~94k pps sustained for two minutes, the flood almost certainly
  saturated the shared `192.168.50.0/24` segment's switch/link capacity rather than exhausting
  anything specific to `.14` — collaterally starving **every** container↔ESP32 and
  Ignition↔container conversation on the LAN, not just the targeted device.
- **Recovery confirmed clean and immediate:** the instant the flood script was stopped (Ctrl-C),
  Ignition and all eight dots came back — Luis directly observed the stop-script → instant-recovery
  correlation. No lasting damage, no manual intervention needed.
- **Conclusion:** Scenario 9 as originally scoped ("isolate one node, the other seven keep
  answering," `Scenarios.md` #9) **was not demonstrated by either vector tried.** What *was*
  demonstrated, convincingly, is a **more severe, broader finding**: this flat, unsegmented network
  means a flood aimed at **one low-value field device** can take down the **entire SCADA visibility
  layer** — a stronger real-world argument for **M0930 Network Segmentation** than the original
  single-node scenario would have made. Worth writing up as its own note rather than forcing it
  into Scenario 9's original framing.

## `s09_synflood.py` built — promotes the working vector to a real script

Reproduced the SYN-flood finding a second time (40.5s @ ~65k pkt/s, 2,634,167 SYNs sent, only 35
SYN-ACK replies — same ~0.001% response rate as the first run; `S09_hping_v2.pcap`, 176 MB, SHA-256
`cc5ce4c5fa1bcc442954ae8f3b27ce8a27eb4c7250a5e3aaee2e0e2498e554fd`, verified identical after
transfer). During this run, **the flood saturated Kali's own uplink badly enough to drop Luis's SSH
session into Kali** — the `hping3` process was confirmed killed (likely `SIGHUP` from the dropped
controlling terminal) rather than left running; `ps aux` showed nothing after reconnecting.

Built `Kali/Scripts/s09_synflood.py` — a thin, **bounded** wrapper around `hping3` (`-c <count>`
instead of an open-ended `--flood`, default 3000 packets ≈ 0.05s at the measured rate, vs. the
2.6–12.3 million packets that caused the outages). Includes a `--dry-run` flag that prints the exact
command without executing it. Docstring records today's findings (the network-wide scope, the
SSH-drop risk, suggests Proxmox console or `tmux` to survive it next time). Added to the manifest
and to `Scenarios.md` #9 (vectors a/b updated with the Nov 23 results; a new note on the real
finding — collateral network-wide DoS as a stronger M0930 argument than the original single-node
scope). **Not run yet** — Luis deliberately held off running even the bounded version today.
