## Update: FH-FireAlarm — board swap, two firmware bugs found and fixed (bench-confirmed)

Started as the deliverable-6/deliverable-5 work (test attack scenarios, fix the FH cascade script), but a live SCADA screenshot showed `FH-FireAlarm Status=2` with the OpenPLC container log repeating `Device FH-FireAlarm-ESP32 is disconnected`, `Connection timed out`/`Bad file descriptor`/`Connection refused`/`Operation now in progress`. Diagnosed before touching the cascade script itself (that work is still pending — see next section).

- **Connectivity:** Luis suspected wiring; checked Serial/LED first (the firmware only ever does steady-green or blinking-red, never blinking-green, per `FH_FireAlarm_Node.ino`, so that symptom didn't match the code). **Luis swapped the ESP32 board and it connected immediately** — root cause confirmed by substitution (a bad board), not diagnosed further; the marginal-Wi-Fi theory already in `STATUS.md` for `.12`/`.22` was not the cause of this particular episode.
- **New false-alarm symptom on the replacement board:** `Alarm=true` with button/flame both false, isolated (by pressing "Alarm OFF" to rule out a stuck remote coil) to `GasSmokeAlert`. Luis identified the sensor as an **MQ-4** (not MQ-2/MQ-9) — closes the "FH gas module model: not recorded" row in `Hardware_BOM.md`. Serial trace showed `gasRaw` climbing steadily for 10-20+ seconds post-boot before leveling off — the existing fixed 2-second post-boot calibration (`calibrateGasSensor()`) was grabbing a baseline mid-drift, latching `GasSmokeAlert` true indefinitely (baseline is only ever set once, at boot).
- **Fix (two passes):** (1) `calibrateGasSensor()` now waits for 5 consecutive 1-second readings to settle within 15 counts (120s timeout) before calibrating, instead of a fixed 2s delay; `setup()` reordered so WiFi/Modbus start before this wait, not after (the first version of this fix calibrated before WiFi, which made the node look disconnected in Ignition for the whole warm-up on every boot — a bug introduced by the fix itself, caught before the first real flash by re-reading the code, not reported by Luis). (2) First real flash still blipped Ignition `Status` 0→1→2→0 during the warm-up (Luis-observed) — `mb.task()` was running so Modbus kept answering, but `heartbeat` only ticks in `loop()`, so `HEARTBEAT` went stale and tripped the Device UDT's staleness rule even though the node was never actually disconnected. Fixed by ticking `heartbeat` once/second during the wait too.
- **Confirmed bench-fixed (not just reported):** Serial transcript shows WiFi connecting before the warm-up trace starts, `baseline=1385`/`alert>1785`, live `gasRaw` (1392, 1328) below threshold with `alarmActive=false (green)`; Luis confirmed `Status` held at 0 through a full reboot after the second flash.
- **New open item, not resolved today:** Luis separately noticed the FH-FireAlarm Wi-Fi dropping in what looked like correlation with FH-PowerBox switching a rail — confirmed **not** the HVAC rail, which rail (if any) still unknown. `Firmware/FH-PowerBox/Schematic/Connections.md` documents (as an **unconfirmed assumption**) that FH-FireAlarm's 5V power is fed through a relay on FH-PowerBox and all three rails share one COM/VIN source — if true, switching one rail could sag the shared supply and brown out another node's Wi-Fi. Not measured with a multimeter.

## Update: VM 100 black console fixed (supersedes "cause not confirmed" above; Luis ran every command)
- **Ruled out (seen):** Proxmox Hardware > Display = Default (VGA); `/sys/module/kernel/parameters/consoleblank` = 0 (idle blanking off); `/proc/cmdline` has no `console=` argument (`quiet splash`, kernel 7.0.0-42-generic, Ubuntu 26.04.1 LTS).
- **Found:** `systemctl get-default` = `graphical.target` on a Docker-only VM. `echo ... | sudo tee /dev/tty1; sudo chvt 1` made "console test" and a cursor appear in the Proxmox console, so the console works but had no login prompt. Most likely cause: the desktop session on that virtual terminal does not render in noVNC. `systemctl status display-manager` and the `dmesg` drm lines were asked for but not sent, so that part is a likely cause, not proven.
