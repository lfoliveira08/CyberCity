## Decisions
| Decision | Rationale |
|---|---|
| New decisions and lessons go in `Logs/`, one file per day. Section 14 of `Piranga_Workflow_v2.md` is frozen as history up to Oct 14, 2026 and its rows are not moved or backfilled | Section 14 had grown to about 60 rows in one table, mixed decisions, bench results and lessons, and was hard to search by day. Many docs cite it as "Section 14, <date> entry", so moving rows would break those references. Starting fresh keeps every old citation valid |
| Every working session ends by writing or updating that day's file and `INDEX.md` | "Everything we do is saved" only holds if the entry is written the same day. Added as a standing instruction in `00_START_HERE.md` Section 9 |
| Stay on OpenPLC v3 through the Dec 11 demo, and plan the move to v4 after it | v4 can do what this architecture needs -- its `modbus_master` plugin is a real Modbus TCP master (pymodbus `ModbusTcpClient`, per-device host/port/slave_id/timeout, FC 1/2/3/4 read and 5/6/15/16 write, per-point cycle time) -- so the blocker was never capability. It was cost and timing: v4 drops the web UI (configuration happens only in the desktop Editor, so nothing to show on screen and one laptop becomes the only way to configure 8 containers), and v4 does not use v3's `%IX100.x` slave block, allocating IEC addresses from a pool starting at 0 instead. That would mean rewriting the address tables in all 8 `Register_Map.md`, `Ladder_Diagram.md` and `Program.st` files, re-verifying all 8 nodes on the bench, and shifting the `PUB_*` addresses that Ignition will poll -- all inside the six weeks before the demo. Rejected: migrating now (schedule risk for no demo-day benefit); staying on v3 permanently (it is archived and unmaintained). Also weighed: v3's weak defaults (plain HTTP, default login, open Modbus server) are useful for the Section 11 attack scenarios, and v3 is the version cited in the ICS security literature |

| OpenPLC Editor projects are saved as `PLC_Logic/<Bldg>-<System>/<Bldg>-<System>-ESP32/`, one per system, with `build/` git-ignored; the hand-written `Program.st` stays the v3 deploy artifact | A new kind of folder needs a registered home before it multiplies to 8 (the `Claude outputs/` lesson). Co-locating with the system keeps one home per system. The v4 Editor compiles ST->C++ for its target and does not export a loose `.st` for the v3 web UI, so the hand-written `Program.st` is what gets uploaded. Registered in `Firmware/WORKFLOW.md` Section 8 and `.gitignore` created at the folder root, same day |
| On every OpenPLC v3 container, turn OFF the S7 and EtherNet/IP servers (both on by default) | The architecture is Modbus-TCP-only; two extra listening services per container contradict the design and add 16 unused open ports across the lab, which would muddy the Section 11 Wireshark captures. Applies to all 8 containers |

## Lessons learned
| Issue | Resolution | Applies to |
|---|---|---|
| A new kind of file with no registered home is how the `Claude outputs/` problem started (Sep 26) | Registered `Logs/` in `Firmware/WORKFLOW.md` Section 8 and `00_START_HERE.md` the same day it was created | Any future new folder |
| OpenPLC v3 is archived and unmaintained as of Apr 4, 2026, so the `openplc:v3` image cannot be rebuilt from a moving upstream and will never be patched | Keep v3 through the demo and migrate to v4 after Dec 11. Record the exact commit the image was built from in `Proxmox_Build_Log.md` so the build is reproducible (the archived repo is frozen, so it is -- but only if the commit is written down) | All 8 OpenPLC containers |
| In OpenPLC Editor 4.2.11, clicking **Remote Devices** in the project tree did nothing, which looked like v4 lacking Modbus master support | Real cause: `Remote Devices` is a folder, not a page. A device is created from the **big blue + button** (create-element), which offers a Remote Device card only when the target declares `modbusTcpRemote` -- `RUNTIME_V4_CAPABILITIES` does, so selecting Device = OpenPLC Runtime v4 first is required. The installed Editor (4.2.11) is also older than the runtime (4.3.1) and the Editor runs a version-compatibility check, so it should be updated to 4.3.x before retesting. **UNVERIFIED:** read from the editor source (`create-element/index.tsx`, `target-capabilities/presets.ts`), not retested in the app after updating | Any future v4 work |
| A Google AI Overview and a container-registry page both gave incomplete answers about v4's Modbus support (one hedged, one mentioned only a `modbus_slave` plugin), which nearly led to the wrong conclusion that v4 could not poll slaves | Cloning both repos and reading the plugin source settled it in minutes. For a decision this size, read the source, not a summary of it | Any future runtime/library evaluation |
