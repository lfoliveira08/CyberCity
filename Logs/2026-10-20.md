### Decisions
| Decision | Rationale |
|---|---|
| Call-floor rungs R1-R3 use a `TP` pulse timer of 300 ms; R4 (`ELEVATOR_DISABLE`) stays a plain level copy | The ESP32 clears the call coils itself and the PLC rewrites them every poll, so a held SCADA bit would send the car back to that floor each time it goes idle. A one-scan `R_TRIG` pulse could be missed because the master writes then sleeps a full Polling Period (read in `modbus_master.cpp`, not measured). `TP` does the edge detection and stretches the pulse. Rejected: option A (plain copy like BSH-Door; simplest, but a held bit pins the car) and B1 (`R_TRIG` only; can lose presses). Different from BSH-Door on purpose, because the consequence of a held bit is different there (it blocks the reader) |
| Task interval `T#20ms` for this project | It is the value Luis saved in his Editor project; the rule is to use the interval set in the Editor and not copy another system's value (BSH-Door uses `T#100ms`). The 300 ms pulse does not depend on it (a timer counts time, not scans) |

### Lessons learned
| Issue | Resolution | Applies to |
|---|---|---|
| A `VAR` block with located variables (`AT %...`) may hold only located variables; mixing in `CALL_PULSE_TIME : TIME` and `TP0 : TP` gave "invalid located variable declaration" plus knock-on errors on every `TP` call. My mistake in the generated `Program.st` | Put unlocated variables (timers, function-block instances, constants) in a second `VAR ... END_VAR` block. Confirmed in the matiec grammar; the second compile succeeded | every `Program.st` that has a timer or function block (FH-HVAC may need one); not BSH-FireAlarm or BSH-Door, where all variables are located |
| A pulse shorter than the polling period can be missed: the OpenPLC master writes the coil buffer, then sleeps the full Polling Period (100 ms), so the loop is a little longer than 100 ms | Stretch the pulse (here `TP`, 300 ms). Read from `modbus_master.cpp`; the miss rate was not measured | any one-shot to a momentary ESP32 coil (BSH-Door if option B is ever added) |
| Log pattern `Connected to MB device` followed by `Connection timed out` and `Bad file descriptor`, repeating: the TCP connection is accepted but the ESP32 does not answer Modbus within the 1000 ms timeout. A ping showed 0% loss and 32 ms average, so it was not the link | Stopped the PLC, unplugged and replugged the ESP32, started the PLC: connected cleanly. **Cause unknown** (unproven guess: stale or full client slots on the ESP32) | all nodes: try an ESP32 power-cycle before suspecting the program or the network |
| The car and the local buttons stopped working although the OLED and Modbus were fine: a motor lead had come off the motor (photo) | Luis repaired it; the local button worked again. Add strain relief to the motor leads. My first guess (lockout left on) was wrong | BSH-Elevator bench; when an actuator stops while the logic looks right, check the wires before the program |
| Monitoring was slow to open right after the first Start PLC, while the log was full of timeouts | Not established; it worked after the ESP32 reboot. The page only talks to this container's own port 502 (read in `webserver.py`) | all containers |
