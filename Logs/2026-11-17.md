## Decisions

| Decision | Rationale |
|---|---|
| Power the BSH-Elevator permanently over a dedicated USB 5V supply, not through the BSH-PowerBox relay rail | The rail fix (dedicated charger feeding the relay's power-side contact) connected and read a good voltage at first, then the node started intermittently disconnecting again under continued use. Time-boxed the troubleshooting rather than open-ended chasing; direct USB power had already been proven stable by substitution on Nov 16. Rejected: continuing to debug the rail wiring/supply sizing further right now, and dropping the Elevator from the project entirely (both considered, see chat). |
| BSH cascade now writes `BSH/Elevator/ElevatorDisable` (coil 3) instead of cutting `BSH/PowerBox/ElevRailCmd` | Once the Elevator is on permanent USB power, the PowerBox can no longer physically cut its power, so the Nov 16 rail-cut cascade script can't work as written. `ELEVATOR_DISABLE` already exists and is already used by Scenario 5's lockout attack, so it's a proven mechanism that works regardless of how the Elevator is powered. Known limit carried over from the firmware's own header comment: `DISABLE` does not stop a move already in progress, only blocks new calls. Rejected: moving the BSH cascade to cut the Door rail instead (an earlier option discussed) — Luis chose `ELEVATOR_DISABLE` specifically. |
| Scenario 6 (building-wide blackout) now targets FH as its primary example; BSH is a documented "2 of 3 nodes" variant | Cutting all three BSH rails no longer drops the Elevator (it's not powered that way anymore), so it's no longer a true 3-node blackout on BSH. FH's three rails all still power real nodes. The script (`s06_blackout.py`) already took a host argument, so no new capability was needed — just which target is the default/primary one. |
| Scenario 7's worked example moved from the Elevator rail (coil 0) to the FireAlarm rail (coil 1) | Same reason as Scenario 6 — coil 0 on BSH no longer controls anything real. The script already took a coil-number argument, so this is a default/documentation change, not new code. |

## Lessons learned

| Issue | Resolution | Applies to |
|---|---|---|
| BSH-PowerBox's Elevator rail relay had COM and NO wired the opposite way from `Connections.md` (COM → Elevator 5V, NO → PowerBox 5V source, instead of the documented COM → PowerBox source, NO → Elevator) | Found by walking through the planned dedicated-supply wiring with Luis and asking him to read back which terminal each wire was actually on, before powering anything. Corrected on the bench and in the doc. | BSH-PowerBox specifically; worth double-checking the same terminals on FH-PowerBox before assuming its doc is correct either, since FH's `Connections.md` is itself marked "assumed to mirror BSH" |
| A dedicated 5V supply wired to the relay's power side connected and read a good voltage, but the node still intermittently disconnected afterward | Not fully root-caused — could be the thin cut-USB-cable wire (recommended shortening/thickening it was never tried), the charger's real sustained current under motor load, a loose breadboard connection, or something not yet identified. Rather than keep debugging an unbounded hardware problem, the fix was changed at the architecture level (permanent USB power + `ELEVATOR_DISABLE` cascade) instead of the wiring level. **Not a lesson that says "dedicated supply doesn't work" — it says this particular ad-hoc bench wiring of one wasn't proven reliable in the time available.** | BSH-Elevator; a caution for anyone later trying the same dedicated-supply approach on the FireAlarm/Door rails — don't assume it's a quick fix without budgeting time to debug marginal connections |
| `STATUS.md`'s open-items entry for this (written Nov 16) said the fix was "chosen but not yet wired or measured" | That text is now stale relative to what actually happened (wired, measured, then abandoned for a different approach) — corrected in place rather than left to mislead the next reader. | `STATUS.md` |
